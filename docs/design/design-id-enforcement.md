# D-000001 — Global Pi design-ID dispatch gate (proposal)

Status: DESIGN; bootstrap number reserved **in this document only**. No gate, approval, or implementation is active. Canonical branch: `design/dispatch-id-gate` (based on `main`). This repository only versions the proposal; the global Pi harness policy is independent of Gateway, Discord channel, target repository and worktree. Ordinary host processes outside the governed Pi launch path are not covered.

1. **Global operator contract and skill UX.** Every governed Pi parent, across sessions/repositories/worktrees (including Discord sessions), must allocate or use a **global** design number and durably log the complete instruction containing it **before each delegated work dispatch** (research, design, implementation, review, follow-up). Package a reusable global skill at `~/.pi/agent/skills/design-work/SKILL.md` with bundled scripts for number reservation, task design/revision, phase and instruction-log operations; agents can use `/skill:design-work` or read it on demand. Design/research/docs-only work may auto-reserve an ID in `DESIGN` without a completed document or approval ceremony; do not create an individual repository design document for each instruction. Implementation requires a task-specific written design linked by global ID with reviewed/approved revision. The parent supervises/reads only: implementation is **always delegated to a child**. Small fixes may use a concise written design, but no prior task authorization silently changes phase: every transition needs a new, explicit attributable owner instruction; existing workflow approval requirements otherwise remain intact.

2. **Single admitted launcher and global record.** Bundled `design-work` scripts expose one shared SQLite ledger/launcher: no separate `log` then unguarded `subagent` step. `new` reserves globally monotonic `D-000001`-style IDs; `dispatch(id, phase, agent, exactInstruction, targetRepo?)` validates and commits a `pending` instruction row before invoking a Pi-subagents child; if logging/validation fails, do not launch. The DB lives outside all repositories/worktrees (private permissions, SQLite `BEGIN IMMEDIATE`, WAL/`synchronous=FULL`): one namespace and phase registry for all governed Pi sessions. Store ID, optional target repo/worktree **as metadata only**, task-specific linked Markdown path when implementation is requested, phase/generation, locked document SHA-256 plus reviewed Git revision, and per-instruction timestamp, exact text/digest, parent session, agent, child run ID, status (`pending/launched/failed/complete`). Before requesting approval **or any phase transition**, send the exact current linked design Markdown to the owner as a downloadable Discord attachment/link (not just a local path or summary); record outbound channel/message ID/time, SHA-256 and reviewed revision, and verify delivery succeeded. If bytes change, re-deliver before asking again. Append a separate transition record with resolved design ID, from/to phase, owner identity, source owner-message ID and timestamp, exact triggering instruction/reference, delivered outbound message ID/digest/revision, design digest/generation and decision time; reject absent/unattributable owner message or a delivery digest that no longer matches the current design. Failed starts remain recorded; never claim `pending` proves launch. The launcher injects/checks `Design: D-...` in every instruction. A thin Pi extension/adapter can use pi-subagents' documented in-process RPC `spawn` to retain its lifecycle; verify the deployed package API before implementation.

3. **Owner-triggered phases and design freeze.** A new ID starts in `DESIGN` (not a transition). All transitions — `DESIGN -> APPROVED -> IMPLEMENT -> COMPLETE` and `IMPLEMENT -> DESIGN` reopen — require an **explicit owner message** identifying the task either by ID or unambiguous current Discord context (for example, “設計OK、実装開始”); the owner need not know or type an ID. The agent resolves the ID before the checker, records the resolved ID and owner-message ID/time, and asks when context is ambiguous instead of silently choosing a task. The agent may suggest a transition, never trigger one automatically from its own judgment, successful review, existing task approval, document creation or child completion. An owner instruction is necessary but **not sufficient**: prior delivery of the same design bytes, serialized state, approved bytes/digest and live-child checks may reject it with a clear reason. Ask only after the attachment/link is accessible in Discord; approval captures the exact delivered Markdown revision, and `IMPLEMENT` starts only if it still matches. Each admitted child obtains a generation-bound active lease. During `IMPLEMENT`, the linked design document is **logically frozen**: the guarded launcher checks its approved SHA-256 before and after every admitted child run and before/after every continuation, blocks any further implementation when it differs, and reports the discrepancy. This detects a changed final document, not every transient mid-run edit; it does **not** mechanically prevent shell/Node/Python/SSH writes or guarantee immutable bytes. On an unexpected need to change it, freeze further implementation immediately, explain the discrepancy, stop/wait for active children (unknown runs block), re-deliver the locked design and **await an explicit owner return-to-DESIGN instruction** before transitioning, invalidating approval/generation, or editing any design bytes. Only after editing/reviewing in `DESIGN` may the owner explicitly approve and then explicitly restart implementation; completion likewise awaits an explicit owner instruction. No automatic lease expiry; recheck digest before dispatch/continuation. SQLite locks coordinate compliant launcher calls, not unrestricted filesystem writes.

4. **Hard gate independent of skill.** `SKILL.md` is on-demand guidance, not authority: Pi can run with `--no-skills`, a model may never read it, and a raw subagent invocation bypasses its scripts. A **global Pi extension** must preflight/deny direct `subagent` launch, steer/resume and parent mutation tools unless the guarded launcher admits them; a controlled Pi entrypoint must require the extension to load successfully (reject `--no-extensions` or missing guard). Before starting/resuming a child, the launcher checks that the linked document digest equals the approved revision; on child exit/continuation completion it rechecks and freezes further work on mismatch. This is a hard *dispatch* gate and a change-detection boundary, not an OS write boundary. If the extension cannot intercept a path, disable that tool/path in the governed profile; an installed skill or an extension that can be omitted does **not** enforce the rule. The governed parent gets read/supervision tools and guarded dispatch, not direct implementation `write`, `edit`, unrestricted `bash`, or other writable extension tools. The admitted implementation worker profile **must not have `subagent` or `allowNestedSubagents`**, and its effective tool list must be checked at launch. Initially admit one materialized child instruction per launch; reject raw `workflowScript`/`workflowScriptPath`, unwrapped named workflows, schedules, external-CLI/external-job writers and any other unadmitted spawn path. Dynamic `runs.run` needs real per-child admission, not outer-script parsing. Treat `steer`, `follow_up`, `resume`/revivals as new instructions: log and check ID/phase/revision *before* delivery/restart or reject; stop/status stay control-only. Reject stale-generation follow-ups. Fail closed if guard, ledger or runtime policy is unavailable.

5. **Selected scope B and honest boundary.** The owner selected B: phase 1 is the global/cross-repository guarded-Pi ID/log prelaunch gate plus approved-document SHA-256 checks before/after each child run and continuation. No per-repo registry/config/CI or macOS OS isolation is required for this selected scope. A mismatch freezes further implementation, preserves evidence and requires explicit owner return-to-DESIGN before any deliberate doc edit; unchanged final bytes do not prove that no transient edit occurred. Parent mutation tools are disabled in the governed profile, but a same-user child with `bash`, Node/Python, custom tools, SSH or remote execution can edit via aliases or restore original bytes before the post-run check; uncontrolled Pi processes, host terminals and external tools likewise remain outside the gate. **Do not describe B as literal write prevention during IMPLEMENT.** A stronger option A would require separately proven OS confinement for parent and all child/remote write paths; it is not selected or activated here. Optional CI catches integration problems later, not mid-run edits. Existing dirty branches get an ID/design prospectively; emergency fixes still need compact design and explicit owner-triggered approval/start.

6. **Integration and acceptance.** After explicit design approval, shared-harness seams are global `~/.pi/agent/skills/design-work/SKILL.md` plus ledger scripts, global Pi guarded prelaunch extension/entrypoint and deployed pi-subagents child launch/RPC. Gateway may launch the guarded profile and its existing `src/discord/send.ts` supports attachments, but is not the policy host; no per-repo config/CI. No skill/script/extension/Gateway code is changed here. Test cross-session/repo ID allocation; `--no-skills` still guarded; missing extension rejected; absent ID/log/approval or changed digest blocks dispatch; nested/raw/opaque launches denied; steer/resume logged or rejected; owner-message evidence required and ambiguity prompts. Send exact current Markdown as accessible Discord attachment before *each* approval/transition request, record outbound digest/revision/message ID, re-deliver on change and attribute inbound owner message ID/time. Check digest before/after every child and continuation including background/resumed runs; changed final bytes freeze further implementation and require explicit owner reopen, while tests must **not** claim prevention of transient edits. Verify active leases and durable instruction row before child start. D-000001 remains DESIGN/unapproved; no implementation begins without the owner's separate explicit design approval and start instruction.
