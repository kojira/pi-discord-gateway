# D-000001 — Governed Discord design-ID dispatch gate (proposal)

Status: DESIGN; bootstrap number reserved **in this document only**. No gate, approval, or implementation is active. Canonical branch: `design/dispatch-id-gate` (based on `main`). This design covers governed Piscord/Discord sessions, not every host process.

1. **Operator contract.** Before *each* delegated work instruction (research, design, implementation, review, follow-up), allocate or use a design number and durably log the complete instruction, containing that number, **before child dispatch**. Design/research/docs-only tasks may auto-reserve a number in `DESIGN` with no completed document or approval ceremony. Implementation requires an existing written design, reviewed/approved revision and `IMPLEMENT` phase. The parent supervises/reads only: implementation is **always delegated to a child**, never edited by the parent. Existing approved small fixes may use a concise written design and their existing authorization as approval only if the owner explicitly accepts that rule; existing workflow approval requirements otherwise remain intact.

2. **Single admitted launcher and record.** A small trusted `design-work` script/command owns both SQLite ledger transaction and launch; no separate `log` then unguarded `subagent` step. `new` reserves monotonic `D-000001`-style IDs; `dispatch(id, phase, agent, exactInstruction, repo)` validates and commits a `pending` instruction row before invoking a Pi-subagents child; if logging or validation fails, do not launch. The DB lives outside disposable worktrees (private permissions, SQLite `BEGIN IMMEDIATE`, WAL/`synchronous=FULL`). Store ID, canonical repo and linked Markdown path, phase/generation, locked document SHA-256 plus reviewed Git revision, approval actor/reference, and per-instruction timestamp, exact text/digest, parent session, agent, repo/worktree, child run ID, status (`pending/launched/failed/complete`). Failed starts remain recorded; never claim a `pending` row proves a child launched. The launcher injects/checks `Design: D-...` in every instruction (not merely conversation history). A thin Pi adapter can use pi-subagents' documented in-process RPC `spawn` to retain normal lifecycle; implementation must first verify this seam against the *deployed* package, not an unrelated npm copy.

3. **Phase and design freeze.** Serialized transitions: `DESIGN -> APPROVED -> IMPLEMENT -> COMPLETE`. Approval captures final written Markdown bytes/revision; `IMPLEMENT` starts only if they still match. Each admitted child obtains a generation-bound active lease; cross-session starts/reopens check leases in the same transaction. In `IMPLEMENT`, editing the linked design document is forbidden **entirely**, including implementation children. If a change is needed: stop/freeze further implementation, wait for every active child to finish/stop (unknown/crashed run stays blocking until reconciled), transition back to `DESIGN` and invalidate the old approval/generation **before any design edit**; review/reapprove changed bytes, then enter a new `IMPLEMENT` generation. No automatic stale-lease expiry; recheck the document digest on admission and before continuation. Locks coordinate compliant launcher calls, not unrestricted filesystem writes.

4. **Close governed child and parent entrypoints.** The governed Discord parent receives read/supervision tools and the guarded launcher, not direct implementation `write`, `edit`, unrestricted `bash`, raw `subagent`, or alternate writable extension tools. The admitted implementation worker profile **must not have `subagent` or `allowNestedSubagents`**, and its effective tool list must be checked at launch; nested fanout is denied, not merely instructed away. For initial rollout, allow only one materialized child instruction per launch: reject raw `workflowScript`/`workflowScriptPath`, unwrapped named workflows, schedules, direct external-CLI/external-job writers and any other unadmitted spawn path. A scripted `runs.run` can create a dynamic task invisible at outer preflight; support it only after a real per-child logging/admission seam exists. `steer`, `follow_up`, `resume` and revived children are *new instructions*: route each through the same ledger/ID/phase/revision check **before delivery or restart**, else reject; stop/status may remain control-only, while any steer that can change work is gated. Reject stale-generation follow-ups. Child capability ceiling can reinforce the no-nesting restriction but is not the instruction log. Fail closed if the adapter, ledger, or deployed runtime policy is unavailable.

5. **Scope and bypasses.** This is an admission gate for governed Discord sessions, **not** a guarantee that local edits cannot occur. Pi's `tool_call` may block `write`/`edit`/`bash` before tool execution, and `user_bash` handles `!`, but arbitrary shell commands, Node/Python, external CLIs, package scripts, custom tools, direct filesystem access, other Pi processes and humans can still write as the host user. In particular, a worker with unrestricted `bash` can rewrite its linked design even when Pi `write` is blocked; an in-process SQLite lock or chmod is not an OS write boundary. To literally prevent *any* implementation edit before approval or *any* design edit during implementation, require an additional OS-enforced workspace policy: design document mounted read-only to all implementation children, source read-only to design children, and no alternate host-writable path; decide/validate this separately before claiming it. Add a required per-repo CI/branch-protection check for implementation PR design ID, externally verifiable approved revision and unchanged linked design document; CI prevents merge, not first local edit. Keep approval evidence outside mutable PR files. Existing dirty branches get an ID/design prospectively, never retroactive compliance; emergency fixes get a short impact/rollback design and approval before dispatch, not a no-design exception.

6. **Integration, acceptance and decision.** Intended seams after approval: Piscord `src/agent/invoke.ts` RPC startup flags (`config.piExtraFlags` must not silently restore forbidden tools), `src/agent/queue.ts`/`src/config.ts` for governed route/adapter binding, external `design-work` ledger/launcher, deployed pi-subagents child profile/launch RPC, and `.github/workflows/ci.yml` plus required branch protection. No code changes in this design branch. Test two concurrent ID allocations and dispatches; missing ID/log, no approved doc, wrong repo, changed digest, failed adapter/spawn; parent direct edit/raw subagent absent; effective worker nested subagent absent; raw scripts/external writer/schedule refused; steer/resume logged and refused after reopen; concurrent active lease blocks reopen; new revision needs reapproval; real Discord child instruction row committed before process start. Explicit owner decision before implementation: **is governed Discord dispatch + protected merge sufficient**, accepting host direct-write bypass, or must all local writers be OS-isolated for literal ANY-edit enforcement? Confirm whether already-authorized small fixes count as design approval. Do not activate until those decisions and the gateway/deployed child runtime checks are complete.
