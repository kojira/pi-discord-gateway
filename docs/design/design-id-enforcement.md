# D-000001 — Global Pi design-ID operations (proposal)

Status: **DESIGN**, unapproved; D-000001 is reserved in this proposal only. Nothing is installed or activated. This is a cross-repository operator policy, not a Gateway or per-repository gate.

1. **Skill and ledger.** A global `~/.pi/agent/skills/design-work/SKILL.md` with bundled script and private SQLite ledger (outside repositories) provides monotonic `D-000001`-style reservation, design linking, phase records, instruction logging and reconciliation. Before **every** delegation (including research, review and follow-up), the parent resolves an ID and logs the exact instruction, parent session, agent, time and intended phase; the script rejects a missing/invalid ID or failed log and does not issue a dispatch instruction. Design/research can reserve an ID without an approved document. Implementation needs a linked, task-specific Markdown design and owner approval. The parent supervises only; implementation is child-only. Small fixes may have a concise design. The ledger records pending/known run IDs and results, but a pending log is not proof of launch. This skill/script is a cooperative path, not an interception point: if the parent uses the native subagent tool after logging, the two steps are not atomic; script validation does not validate an independently launched child.

2. **Owner authority and approved bytes.** Every transition (`DESIGN -> APPROVED -> IMPLEMENT -> COMPLETE`, or `IMPLEMENT -> DESIGN` to reopen) requires a **new, explicit, attributable owner message**; prior approval, a completed child, or agent judgment cannot advance phase. Resolve an owner reference by ID or unambiguous current context, otherwise ask. Before seeking approval or another transition, attach/link the **exact current Markdown bytes** for the owner to access (not a summary/path alone); record outbound message ID, SHA-256 and revision with the inbound owner message ID/time. Reattach if bytes change. Approval locks that delivered digest/revision; a separate explicit start instruction enters IMPLEMENT only if the design still matches. On a needed redesign, stop further implementation, await the owner's explicit return-to-DESIGN, revise and reattach, then obtain fresh explicit approval and start. Completion also requires explicit owner instruction.

3. **Compromise B: detection, not prevention.** For each cooperatively dispatched implementation child/continuation, compare the linked design's SHA-256 to the approved digest **before and after** the run; hold further implementation and delivery/merge on mismatch, retain evidence and seek owner review. Check before a follow-up/resume as a new logged instruction. Unknown/running children block a claim that checks are complete. A final-byte check can miss edits reverted during a run; it cannot prevent writes by a child, parent shell, another process or remote actor. B remains a digest-based detection compromise, not immutable design bytes or OS isolation. No Pi core, extension, pi-subagents modification, controlled Pi entrypoint, RPC adapter, per-repo CI or OS confinement is required or claimed.

4. **Parent-issued instruction audit (proposed detection boundary).** The authoritative evidence for *model-issued `subagent` tool instructions from this Discord parent* is its persisted Pi session JSONL, not a scan for child artifacts. Piscord starts Pi in RPC mode with `--session-dir <sessionsDir>/<channelFolder> --continue` (`src/agent/invoke.ts`); rotation moves a channel directory to `<channelFolder>__archived_<timestamp>` (`src/session/path.ts`). Maintain a durable inventory of every parent session-file path and last reconciled byte offset/digest across active and archived channel directories, including new session files after rotation/restart and any session that issued an instruction for this design. Do not infer completeness merely from a current channel's latest file. At the end of **each completed parent turn, before any child output is delivered, reused or merged**, snapshot all inventoried parent transcripts through that turn and reconcile *every* `type:"message"`, `message.role:"assistant"`, `message.content[]` item with `type:"toolCall"`, `name:"subagent"` by session identity, entry ID and tool-call ID against the instruction ledger. The call's `arguments` are the parent-issued instruction: single `agent`/`task`; `workflowScript` (or `workflowScriptPath`, whose referenced bytes must also be preserved and checked); management `action:"resume"`/`"steer"` with `id`/`runId`/`dir`, `message`, `mode`/index; and any other execution-capable action, including schedule creation/execution. Do not count read-only status/list calls as delegations, but never discard an unrecognized action as harmless. An `action:"resume"` is a *new* instruction even when it reuses an existing child session; a steer is also an instruction, not proof of a new child launch. Workflow calls may issue multiple child instructions and resume/steer within `runs.run`/`runs.all`/`runs.steer`; reconcile the submitted script and each actual child/continuation receipt to ledger entries, and block if dynamic instruction bytes or child identities cannot be established. Match `message.role:"toolResult"` by `toolCallId` to correlate any available `details.runId`, `mode`, `results`/`workflowChildren` and `asyncDir`; child run IDs and async `status.json`/`events.jsonl` supplement the audit, never replace the originating tool call. A pending call with no result is unresolved, not evidence that it did not run.

   This is a **conditional late-detection guarantee for retained, complete parent-session tool calls**, not a dispatch guard. Pi persists assistant messages at `message_end` before tool execution (`agent-session.js`), so a completed parent turn's calls are enumerable even when an async/foreground child artifact has disappeared. A missing session file, changed/truncated prior checkpoint, malformed/incomplete JSONL record, inaccessible referenced workflow script, absent result/child receipt where required to prove dispatch or individual child instructions, unresolved in-flight call, lost root after archive cleanup, or inability to verify that all parent turns/files since the prior checkpoint were included **fails closed**: do not certify compliance or deliver/reuse/merge output; preserve the available evidence and ask the owner to review. Keep checkpoint/inventory evidence outside expiring session/async roots; `ARCHIVE_RETENTION_DAYS` defaults to 30 in Gateway, while pi-subagents temporary artifacts and completion replay can expire sooner. Do not certify any interval whose parent transcript was removed before a complete audit. If a tool call has no matching valid ledger instruction, mark it an orphan and quarantine related output/changes before owner review. An operator must actually perform this independent reconciliation at the gate; asking a non-cooperating parent to self-attest does not enforce it. Human interactive Pi TUI, another parent session not in the inventory, an independent external CLI/RPC process, or a parent shell/CLI path not captured as a `subagent` tool call is **outside this proven tool-call boundary**; the latter cannot be silently classified as audited. There is no verified universal run audit, no interception or prelaunch block without a hook, and no guarantee against deletion/tampering with both the source transcript and independent audit checkpoint. D-000001 remains DESIGN: this document authorizes no implementation.
