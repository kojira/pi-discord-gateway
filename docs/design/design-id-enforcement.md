# D-000001 — Global Pi design-ID operations (proposal)

Status: **DESIGN**, unapproved; D-000001 is reserved in this proposal only. Nothing is installed or activated. This is a cross-repository operator policy, not a Gateway or per-repository gate.

1. **Skill and ledger.** A global `~/.pi/agent/skills/design-work/SKILL.md` with bundled script and private SQLite ledger (outside repositories) provides monotonic `D-000001`-style reservation, design linking, phase records, instruction logging and reconciliation. Before **every** delegation (including research, review and follow-up), the parent resolves an ID and logs the exact instruction, parent session, agent, time and intended phase; the script rejects a missing/invalid ID or failed log and does not issue a dispatch instruction. Design/research can reserve an ID without an approved document. Implementation needs a linked, task-specific Markdown design and owner approval. The parent supervises only; implementation is child-only. Small fixes may have a concise design. The ledger records pending/known run IDs and results, but a pending log is not proof of launch. This skill/script is a cooperative path, not an interception point: if the parent uses the native subagent tool after logging, the two steps are not atomic; script validation does not validate an independently launched child.

2. **Owner authority and approved bytes.** Every transition (`DESIGN -> APPROVED -> IMPLEMENT -> COMPLETE`, or `IMPLEMENT -> DESIGN` to reopen) requires a **new, explicit, attributable owner message**; prior approval, a completed child, or agent judgment cannot advance phase. Resolve an owner reference by ID or unambiguous current context, otherwise ask. Before seeking approval or another transition, attach/link the **exact current Markdown bytes** for the owner to access (not a summary/path alone); record outbound message ID, SHA-256 and revision with the inbound owner message ID/time. Reattach if bytes change. Approval locks that delivered digest/revision; a separate explicit start instruction enters IMPLEMENT only if the design still matches. On a needed redesign, stop further implementation, await the owner's explicit return-to-DESIGN, revise and reattach, then obtain fresh explicit approval and start. Completion also requires explicit owner instruction.

3. **Compromise B: detection, not prevention.** For each cooperatively dispatched implementation child/continuation, compare the linked design's SHA-256 to the approved digest **before and after** the run; hold further implementation and delivery/merge on mismatch, retain evidence and seek owner review. Check before a follow-up/resume as a new logged instruction. Unknown/running children block a claim that checks are complete. A final-byte check can miss edits reverted during a run; it cannot prevent writes by a child, parent shell, another process or remote actor. B remains a digest-based detection compromise, not immutable design bytes or OS isolation. No Pi core, extension, pi-subagents modification, controlled Pi entrypoint, RPC adapter, per-repo CI or OS confinement is required or claimed.

4. **Late reconciliation and limits.** Before delivering child output or merging changes, the operator reconciles ledger instructions/run IDs against **available** pi-subagents run status, session transcripts and artifacts in known session/async roots; investigate unmatched run/output evidence as an orphan, quarantine its output/changes from delivery/merge, and ask the owner to review before reuse. Unknown status, missing evidence or cleanup means do not certify the run as compliant. The installed `pi-subagents` 0.64.0 documents async `status.json`/`events.jsonl` and run IDs, plus optional per-run input/output/metadata artifacts (`docs/observability.md`, “Async run artifacts” and “Workflow and debug artifacts”); result replay is temporary, artifacts may be disabled or cleaned, and foreground/other-session/raw CLI/TUI activity is not guaranteed to appear in these roots. There is **no verified universal run audit** and no prelaunch block for raw subagent/TUI/CLI invocations without a Pi hook. Reconciliation is best-effort for visible evidence, not proof that no bypass occurred. Validate roots, retention, receipt correlation and script-to-launch handoff in a later implementation design before promising wider coverage. D-000001 remains DESIGN: this document authorizes no implementation.
