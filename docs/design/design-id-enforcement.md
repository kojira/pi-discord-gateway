# D-000001 — Global Pi design-ID dispatch gate (proposal)

Status: DESIGN; bootstrap number reserved **in this document only**. No gate, approval, or implementation is active. Canonical branch: `design/dispatch-id-gate` (based on `main`). This repository only versions the proposal; the global Pi harness policy is independent of Gateway, Discord channel, target repository and worktree. Ordinary host processes outside the governed Pi launch path are not covered.

1. **Global operator contract and skill UX.** Every governed Pi parent, across sessions/repositories/worktrees (including Discord sessions), must allocate or use a **global** design number and durably log the complete instruction containing it **before each delegated work dispatch** (research, design, implementation, review, follow-up). Package a reusable global skill at `~/.pi/agent/skills/design-work/SKILL.md` with bundled scripts for number reservation, task design/revision, phase and instruction-log operations; agents can use `/skill:design-work` or read it on demand. Design/research/docs-only work may auto-reserve an ID in `DESIGN` without a completed document or approval ceremony; do not create an individual repository design document for each instruction. Implementation requires a task-specific written design linked by global ID with reviewed/approved revision. The parent supervises/reads only: implementation is **always delegated to a child**. Small fixes may use a concise written design, but no prior task authorization silently changes phase: every transition needs a new, explicit attributable owner instruction; existing workflow approval requirements otherwise remain intact.

2. **Single admitted launcher and global record.** Bundled `design-work` scripts expose one shared SQLite ledger/launcher: no separate `log` then unguarded `subagent` step. `new` reserves globally monotonic `D-000001`-style IDs; `dispatch(id, phase, agent, exactInstruction, targetRepo?)` validates and commits a `pending` instruction row before invoking a Pi-subagents child; if logging/validation fails, do not launch. The DB lives outside all repositories/worktrees (private permissions, SQLite `BEGIN IMMEDIATE`, WAL/`synchronous=FULL`): one namespace and phase registry for all governed Pi sessions. Store ID, optional target repo/worktree **as metadata only**, task-specific linked Markdown path when implementation is requested, phase/generation, locked document SHA-256 plus reviewed Git revision, and per-instruction timestamp, exact text/digest, parent session, agent, child run ID, status (`pending/launched/failed/complete`). Append a separate transition record with resolved design ID, from/to phase, owner identity, source owner-message ID and timestamp, exact triggering instruction/reference, design digest/generation and decision time; reject transitions without an attributable owner message. Failed starts remain recorded; never claim `pending` proves launch. The launcher injects/checks `Design: D-...` in every instruction. A thin Pi extension/adapter can use pi-subagents' documented in-process RPC `spawn` to retain its lifecycle; verify the deployed package API before implementation.

3. **Owner-triggered phases and design freeze.** A new ID starts in `DESIGN` (not a transition). All transitions — `DESIGN -> APPROVED -> IMPLEMENT -> COMPLETE` and `IMPLEMENT -> DESIGN` reopen — require an **explicit owner message** identifying the task either by ID or unambiguous current Discord context (for example, “設計OK、実装開始”); the owner need not know or type an ID. The agent resolves the ID before the checker, records the resolved ID and owner-message ID/time, and asks when context is ambiguous instead of silently choosing a task. The agent may suggest a transition, never trigger one automatically from its own judgment, successful review, existing task approval, document creation or child completion. An owner instruction is necessary but **not sufficient**: serialized state, approved bytes/digest and live-child checks may reject it with a clear reason. Approval captures reviewed Markdown revision; `IMPLEMENT` starts only if it still matches. Each admitted child obtains a generation-bound active lease. During `IMPLEMENT`, the linked design document must not be edited, even by implementation children. On an unexpected need to change it, freeze further implementation immediately, explain the discrepancy, stop/wait for active children (unknown runs block) and **await an explicit owner return-to-DESIGN instruction** before transitioning, invalidating approval/generation, or editing any design bytes. Only after editing/reviewing in `DESIGN` may the owner explicitly approve and then explicitly restart implementation; completion likewise awaits an explicit owner instruction. No automatic lease expiry; recheck digest before dispatch/continuation. SQLite locks coordinate compliant launcher calls, not unrestricted filesystem writes.

4. **Hard gate independent of skill.** `SKILL.md` is on-demand guidance, not authority: Pi can run with `--no-skills`, a model may never read it, and a raw subagent invocation bypasses its scripts. A **global Pi extension** must preflight/deny direct `subagent` launch, steer/resume and parent mutation tools unless the guarded launcher admits them; a controlled Pi entrypoint must require the extension to load successfully (reject `--no-extensions` or missing guard). If the extension cannot intercept a path, disable that tool/path in the governed profile; an installed skill or an extension that can be omitted does **not** enforce the rule. The governed parent gets read/supervision tools and guarded dispatch, not direct implementation `write`, `edit`, unrestricted `bash`, or other writable extension tools. The admitted implementation worker profile **must not have `subagent` or `allowNestedSubagents`**, and its effective tool list must be checked at launch. Initially admit one materialized child instruction per launch; reject raw `workflowScript`/`workflowScriptPath`, unwrapped named workflows, schedules, external-CLI/external-job writers and any other unadmitted spawn path. Dynamic `runs.run` needs real per-child admission, not outer-script parsing. Treat `steer`, `follow_up`, `resume`/revivals as new instructions: log and check ID/phase/revision *before* delivery/restart or reject; stop/status stay control-only. Reject stale-generation follow-ups. Fail closed if guard, ledger or runtime policy is unavailable.

5. **Scope and bypasses.** Phase 1 is a **global cross-repository admission gate for Pi sessions launched with the mandatory guard**, including governed Discord sessions; no per-repository registry, configuration, CI or branch protection is required. Skill-only use, `--no-extensions`/uncontrolled Pi launches and direct external tools are outside its enforceable boundary. This is **not** a guarantee that local edits cannot occur: even Pi `tool_call`/`user_bash` interception cannot identify every side effect of arbitrary shell, Node/Python, package scripts, custom tools or external CLI. Another Pi process or human can write as the host user; a worker with unrestricted `bash` can rewrite its linked design even when Pi `write` is blocked. SQLite locks/chmod are not OS write boundaries. For literal prevention of *any* implementation edit before approval or design edit during implementation, separately approve OS-enforced workspaces with linked design read-only to implementation children, source read-only to design children, and no alternate host-writable path. Optional downstream CI catches integration errors later, never replaces prelaunch admission. Existing dirty branches get an ID/design prospectively; emergency fixes get a short impact/rollback design and explicit owner-triggered approval/start before implementation dispatch, not a no-design exception.

6. **Integration, acceptance and decision.** Intended shared-harness seams after approval: global `~/.pi/agent/skills/design-work/SKILL.md` and bundled ledger scripts, global Pi prelaunch extension/guarded entrypoint, deployed pi-subagents child profile/launch RPC. Gateway may launch the same guarded Pi profile (its `src/agent/invoke.ts` startup flags must not disable the guard), but is **not** the policy host or required UX; no per-repo config/CI integration. No skill, script, extension or Gateway code is changed here. Test concurrent global ID allocation and cross-session/cross-repo dispatch; skill omitted/`--no-skills` still guarded; `--no-extensions`/missing extension rejected at entrypoint; absent ID/log/approved implementation design or changed digest blocks; parent mutation/raw subagent absent; worker nested subagent absent; raw scripts/external writers/schedules refused; steer/resume logged or refused after reopen; concurrent leases block owner-requested reopen; all phase transitions reject absent/unattributable owner message even when checks pass, resolve an unambiguous context-only message to the ID before checking and ask on ambiguity, log resolved ID plus owner-message ID/time when accepted, and reject stale digest/active child even when requested; surprise design changes freeze work pending owner reopen, then separately requested reapproval/restart; child instruction row committed before process starts. Explicit owner decision before implementation: **is guarded global Pi dispatch sufficient**, accepting uncontrolled host-write bypass, or must all local writers be OS-isolated for literal ANY-edit enforcement? Do not activate until those decisions and deployed runtime checks complete.
