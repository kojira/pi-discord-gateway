# D-000001 — Global cross-repository Discord design-ID dispatch gate (proposal)

Status: DESIGN; bootstrap number reserved **in this document only**. No gate, approval, or implementation is active. Canonical branch: `design/dispatch-id-gate` (based on `main`). This file's location and the Gateway are versioned source/integration hosts, **not policy boundaries**: the one global rule applies to every governed Discord parent session and its delegated instructions, regardless of target repository or worktree, not to arbitrary host processes.

1. **Global operator contract.** Every governed Discord parent, across sessions/repositories/worktrees, must allocate or use a **global** design number and durably log the complete instruction containing that number **before each delegated work dispatch** (research, design, implementation, review, follow-up). Design/research/docs-only work may auto-reserve an ID in `DESIGN` with no completed document or approval ceremony; do not create an individual repository design document for each instruction. When implementation is requested, the global ID must link to the task-specific written design and its reviewed/approved revision before `IMPLEMENT` begins. The parent supervises/reads only: implementation is **always delegated to a child**, never edited by the parent. Existing approved small fixes may use a concise written design and their existing authorization as approval only if the owner explicitly accepts that rule; existing workflow approval requirements otherwise remain intact.

2. **Single admitted launcher and global record.** A small trusted `design-work` script/command owns both global SQLite ledger transaction and launch; no separate `log` then unguarded `subagent` step. `new` reserves globally monotonic `D-000001`-style IDs; `dispatch(id, phase, agent, exactInstruction, targetRepo?)` validates and commits a `pending` instruction row before invoking a Pi-subagents child; if logging or validation fails, do not launch. The DB lives outside all repositories/worktrees (private permissions, SQLite `BEGIN IMMEDIATE`, WAL/`synchronous=FULL`): one namespace and one phase registry for every governed Discord session. Store ID, optional target repo/worktree **as metadata only** (never a per-repo ID registry or prerequisite), linked task-specific Markdown path when implementation is requested, phase/generation, locked document SHA-256 plus reviewed Git revision, approval actor/reference, and per-instruction timestamp, exact text/digest, parent session, agent, child run ID, status (`pending/launched/failed/complete`). Failed starts remain recorded; never claim a `pending` row proves a child launched. The launcher injects/checks `Design: D-...` in every instruction (not merely conversation history). A thin Pi adapter can use pi-subagents' documented in-process RPC `spawn` to retain normal lifecycle; implementation must first verify this seam against the *deployed* package, not an unrelated npm copy.

3. **Phase and design freeze.** Serialized transitions: `DESIGN -> APPROVED -> IMPLEMENT -> COMPLETE`. Approval captures final written Markdown bytes/revision; `IMPLEMENT` starts only if they still match. Each admitted child obtains a generation-bound active lease; cross-session starts/reopens check leases in the same transaction. In `IMPLEMENT`, editing the linked design document is forbidden **entirely**, including implementation children. If a change is needed: stop/freeze further implementation, wait for every active child to finish/stop (unknown/crashed run stays blocking until reconciled), transition back to `DESIGN` and invalidate the old approval/generation **before any design edit**; review/reapprove changed bytes, then enter a new `IMPLEMENT` generation. No automatic stale-lease expiry; recheck the document digest on admission and before continuation. Locks coordinate compliant launcher calls, not unrestricted filesystem writes.

4. **Close governed child and parent entrypoints.** The governed Discord parent receives read/supervision tools and the guarded launcher, not direct implementation `write`, `edit`, unrestricted `bash`, raw `subagent`, or alternate writable extension tools. The admitted implementation worker profile **must not have `subagent` or `allowNestedSubagents`**, and its effective tool list must be checked at launch; nested fanout is denied, not merely instructed away. For initial rollout, allow only one materialized child instruction per launch: reject raw `workflowScript`/`workflowScriptPath`, unwrapped named workflows, schedules, direct external-CLI/external-job writers and any other unadmitted spawn path. A scripted `runs.run` can create a dynamic task invisible at outer preflight; support it only after a real per-child logging/admission seam exists. `steer`, `follow_up`, `resume` and revived children are *new instructions*: route each through the same ledger/ID/phase/revision check **before delivery or restart**, else reject; stop/status may remain control-only, while any steer that can change work is gated. Reject stale-generation follow-ups. Child capability ceiling can reinforce the no-nesting restriction but is not the instruction log. Fail closed if the adapter, ledger, or deployed runtime policy is unavailable.

5. **Scope and bypasses.** Phase 1 is a **global cross-repository admission gate for governed Discord sessions**; it needs no per-repository registry, configuration, CI or branch protection to decide dispatch. It is **not** a guarantee that local edits cannot occur. Pi's `tool_call` may block `write`/`edit`/`bash` before execution, and `user_bash` handles `!`, but arbitrary shell commands, Node/Python, external CLIs, package scripts, custom tools, direct filesystem access, other Pi processes and humans can still write as the host user. In particular, a worker with unrestricted `bash` can rewrite its linked design even when Pi `write` is blocked; an in-process SQLite lock or chmod is not an OS write boundary. For literal prevention of *any* implementation edit before approval or *any* design edit during implementation, a separately approved OS-enforced workspace policy must make the linked design read-only to implementation children and implementation source read-only to design children, without alternate host-writable paths. Optional downstream CI would catch integration errors later, never serve as phase-1 admission or first-edit enforcement. Existing dirty branches get a global ID/design prospectively, never retroactive compliance; emergency fixes get a short impact/rollback design and approval before dispatch, not a no-design exception.

6. **Integration, acceptance and decision.** Intended shared-harness seams after approval: Piscord `src/agent/invoke.ts` RPC startup flags (`config.piExtraFlags` must not silently restore forbidden tools), `src/agent/queue.ts`/`src/config.ts` for the common parent adapter across all Discord sessions, external global `design-work` ledger/launcher, and deployed pi-subagents child profile/launch RPC. No per-repo config/CI integration is required; no code changes in this design branch. Test concurrent global ID allocation and cross-session/cross-repo dispatch; missing ID/log, no approved implementation document, changed digest, failed adapter/spawn; parent direct edit/raw subagent absent; effective worker nested subagent absent; raw scripts/external writer/schedule refused; steer/resume logged and refused after reopen; concurrent active lease blocks reopen; new revision needs reapproval; real Discord child instruction row committed before process start. Explicit owner decision before implementation: **is global governed Discord dispatch sufficient**, accepting direct host-write bypass, or must all local writers be OS-isolated for literal ANY-edit enforcement? Confirm whether already-authorized small fixes count as design approval. Do not activate until those decisions and the gateway/deployed child runtime checks are complete.
